title: Calls and TURN
description: Running coturn so calls connect from the hardest networks, and issuing time-limited credentials.
---

Calls are WebRTC. Signaling rides inside the sealed DM envelope, so a relay can
route a call without reading it. Media never touches a relay unless a direct
path fails and TURN is used as a fallback.

## When TURN is actually needed

Most calls connect directly, or with the help of STUN. TURN only matters when
a direct path cannot be established at all — the classic case being two peers
behind symmetric NAT, or one behind a corporate or carrier-grade NAT.

A rough rule: if calls fail to connect only on one network, that network is the
one that needs TURN. There is no need to run a TURN server for everyone to
improve the common case.

## Ports

coturn needs three things reachable from the internet:

| Port | Protocol | Purpose |
|---|---|---|
| 3478 | TCP and UDP | Client connection and allocation |
| 49152–65535 | UDP | Relay: the media itself |

The relay range is the one people miss. Only 3478 being open produces a server
that accepts requests and then sends media nowhere.

If you run a firewall, open both. With `ufw`:

```
ufw allow 3478/tcp
ufw allow 3478/udp
ufw allow 49152:65535/udp
```

## Configuration

Install coturn, then use `/etc/turnserver.conf`. The settings that matter:

```
listening-port=3478
tls-listening-port=5349
fingerprint
lt-cred-mech
use-auth-secret

# Generate once, keep it secret, and keep it stable. Changing it invalidates
# every credential you have issued.
static-auth-secret=REPLACE_WITH_A_LONG_RANDOM_STRING

realm=turn.example.com
external-ip=203.0.113.10

# The relay range, stated explicitly so it is not derived differently by
# different coturn versions.
min-port=49152
max-port=65535

# A node should not be an open relay for the whole internet.
no-multicast-peers
denied-peer-ip=0.0.0.0-0.255.255.255
denied-peer-ip=10.0.0.0-10.255.255.255
denied-peer-ip=169.254.0.0-169.254.255.255
denied-peer-ip=172.16.0.0-172.31.255.255
denied-peer-ip=192.168.0.0-192.168.255.255
denied-peer-ip=127.0.0.0-127.255.255.255
```

`external-ip` is the public address of the host, which is rarely what the
interface reports. If it is wrong, clients allocate successfully and then
receive no media.

Enable the service:

```
systemctl enable --now coturn
```

## Time-limited credentials

Do not put a static TURN username and password in the client. The Peers build
compiles `VITE_TURN_*` into the bundle, so a static credential is readable by
anyone who has the application. That is fine for a server you control and
entirely wrong for a shared deployment.

coturn solves this with a shared secret and a small REST API. The client asks
your server for a credential that expires, and your server signs it with a
secret it never sends.

**Requesting a credential.** The username is the expiry time as a Unix
timestamp, and the password is a base64 HMAC-SHA1 of that username, keyed by the
shared secret as ASCII text:

```
GET /turn?urn:ietf:params:xml:ns:turn:api:allocate
```

The response is XML containing `<username>` and `<password>`. Hand those to the
client and they are valid until the timestamp passes.

**Issuing one server-side** (Node, matching the rest of this stack):

```js
import {createHmac} from "node:crypto";

const TURN_SECRET = process.env.TURN_SHARED_SECRET;
const TURN_TTL_SECONDS = 24 * 60 * 60;

export async function issueTurnCredential() {
  const username = String(Math.floor(Date.now() / 1000) + TURN_TTL_SECONDS);
  const credential = createHmac("sha1", TURN_SECRET).update(username).digest("base64");
  return {
    username,
    credential,
    // Urls for the client to configure.
    urls: ["turn:turn.example.com:3478?transport=udp", "turn:turn.example.com:3478?transport=tcp"],
    ttl: TURN_TTL_SECONDS,
  };
}
```

Keep the endpoint unauthenticated only if you are comfortable with it minting
credentials for anyone who asks — rate limit it, or put it behind your own
account check, since a credential is a billable relay allocation.

## Pointing the client at it

`coturn` cannot hand out a credential at build time, so this has two parts: the
client needs a URL and a way to get short-lived credentials at runtime.

| Variable | Purpose |
|---|---|
| `VITE_STUN_URL` | STUN server. Defaults to a public Google STUN. |
| `VITE_TURN_URL` | TURN URL. Required for any TURN to be used. |
| `VITE_TURN_USERNAME` | Only set this for a self-hosted server you control. |
| `VITE_TURN_CREDENTIAL` | Same. Leave unset when using runtime credentials. |

TURN is only enabled when the URL, username, and credential are **all** present.
A TURN entry with missing credentials can fail ICE outright rather than falling
back to STUN, so a half-configured value is worse than none — it is dropped
rather than half-applied.

For a shared deployment, leave `VITE_TURN_USERNAME` and
`VITE_TURN_CREDENTIAL` unset, set only `VITE_TURN_URL`, and fetch a fresh
username and credential at runtime from your own endpoint. That keeps long-lived
secrets out of the bundle entirely.

## Checking it works

From the server, confirm coturn is listening and has your realm:

```
ss -lnup | grep 3478
```

From a client, a successful call that had been failing is the real test. A
useful signal is that coturn logs an allocation. On the client side, WebRTC
reports which candidate type won: `relay` means TURN carried the media,
`srflx` means STUN sufficed, and `host` means it was direct.

To force the TURN path while testing, block direct connections on one side.
Confirming a call connects *with* TURN configured is the only way to know the
relay range and `external-ip` are right, since a working direct path hides both
problems.
