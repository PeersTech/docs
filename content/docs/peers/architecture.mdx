## Overview

Peers is a Tauri 2 app. The Rust backend handles all cryptographic operations and P2P networking. The React frontend is the user interface.

## Security model

The frontend is primarily a presentation shell. Derived private keys and direct-message decryption stay in the Rust backend. The Tauri `invoke()` boundary is the local client boundary, with one explicit onboarding exception: the recovery phrase is displayed locally so the user can save it, then passed back to the backend.

The network has different confidentiality contracts. Direct messages are sealed envelopes between the intended peers. Server-channel messages, Plaza messages, server/member notices, and relay-control notices are signed or plaintext application payloads. A relay or other subscribed peer can observe those payloads and their routing metadata; libp2p transport encryption does not turn them into end-to-end secrets.

```
+-----------------------------------------------------+
|                    Frontend                          |
|              React 19 + TypeScript                   |
|                                                      |
|   +----------------------------------------------+   |
|   |            Tauri invoke() boundary            |   |

|                          |                           |

|                    Backend                           |
```

## Discovery, reachability, relaying

Three different jobs, often confused:

| Job | What it means | How Peers does it |
|---|---|---|
| Discovery | Finding where a peer is | Public IPFS DHT plus gossipsub meshes. Free, already working. |
| Reachability | Being dialable at all | Impossible behind a home router. Needs a public node. |
| Relaying | Carrying traffic when neither side is dialable | Only a machine with a public address, via Circuit Relay v2. |

DHT bootstrap is not relaying. Peers resolves `_dnsaddr.bootstrap.libp2p.io` TXT records for the public IPFS bootstrap nodes. They help find peers and route DHT queries; they are not a Peers group-chat service. The application-level confidentiality guarantee still depends on the topic payload: sealed DMs remain sealed, while signed or plaintext topics do not.

Node discovery for relaying is manual today: operators hand out a `PEERS_NODES=` line, and clients paste it into the `PEERS_NODES` env var or `<config>/peers/nodes.json` (a JSON array of multiaddr strings, each ending in `/p2p/<peer-id>`). The env var wins when both are present. The project plan explicitly ships no canonical public node list, since that would make those nodes a de facto central dependency.

## Bootstrap flow

On startup, headless or GUI:

1. Read `PEERS_NODES`. Split on commas, parse each as a multiaddr. If any parse, use them and never read `nodes.json`.
2. Otherwise read `<config>/peers/nodes.json` as an array of multiaddr strings. Invalid entries are skipped silently.
3. Dial every known node and reserve a relay slot on each, retrying with exponential backoff from 10 seconds up to a 5-minute ceiling.
4. After a short delay, resolve the public IPFS bootstrap via DNS TXT and join the Kademlia DHT.
5. Subscribe to gossipsub topics (DM, friend requests, servers, Plaza) and publish a subscribe notice on the shared `peers/v1/relay` topic so backbone nodes mesh them.

GUI clients listen on an ephemeral port. Nobody dials a client by address. Clients are reached over relay circuits.

## Relay tiers

Every Peers process is a node that routes gossip, seeds blobs, and relays connections. A `--node` process is not a special build, just a different tier of the same binary. Whether an install actually relays is decided by reachability: an unreachable client advertises slots harmlessly, because nobody can dial it.

| Tier | Reservations | Circuits | Per circuit | Who |
|---|---|---|---|---|
| `citizen` | 8 (2/peer) | 16 (2/peer) | 16 MiB | Every GUI client |
| `node` | 64 (4/peer) | 64 (8/peer) | 128 MiB | `--node` |
| `off` | 0 | 0 | none | `PEERS_NO_RELAY=1` |

Raw connection limits sit above the relay caps, so the relay budget stays the binding constraint:

| Tier | Pending in/out | Established in/out | Per peer | Who |
|---|---|---|---|---|
| `client` | 16 / 32 | 64 / 128 | 8 | GUI clients |
| `node` | 64 / 64 | 512 / 256 | 8 | `--node` |

## Crypto module

| File | Purpose |
|---|---|
| `identity.rs` | Ed25519 keypair plus X25519 static secret, deterministic from entropy |
| `keystore.rs` | Version 2 sealed keystore (Argon2id KDF plus XChaCha20-Poly1305). Version 1 is refused. |
| `seed.rs` | HKDF domain-separated derivation from mnemonic entropy |
| `mnemonic.rs` | BIP39 12/24-word mnemonic generate, decode, encode |
| `cipher.rs` | ChaCha20-Poly1305 AEAD seal/open with sequence-based nonces |
| `session.rs` | Per-contact keys: `key_n = HKDF(SHA256^n(root))`, random per-process envelope nonces, replay protection, out-of-order delivery |
| `group.rs` | Signed group descriptors and private group invitations |
| `card.rs` | Self-authenticating peer cards, multi-recipient sealed envelopes |
| `code.rs` | 12-digit short peer codes, used as DHT rendezvous keys |
| `server.rs` | Servers, channels, roles, ACLs, invites, snapshots |

## P2P module

| File | Purpose |
|---|---|
| `mod.rs` | Node event loop, swarm handling, relay management with backoff |
| `behaviour.rs` | Identify, ping, Kademlia, gossipsub, relay, DCUtR, AutoNAT, request-response |
| `blobs.rs` | Content-addressed blob store (SHA-256), torrent-style DHT parking |
| `bootstrap.rs` | `PEERS_NODES` / `nodes.json` / `PEERS_PORT` / `PEERS_ANNOUNCE`, DNS bootstrap |

## Network transports

TCP for reliability, QUIC over UDP for faster setup, Noise for the connection handshake, and Yamux for stream multiplexing. Noise protects the libp2p connection between its endpoints; it does not change the application payload from plaintext server, Plaza, or control traffic into an end-to-end secret.

## State persistence

GUI identity and application state are sealed at rest with Argon2id plus
XChaCha20-Poly1305:

- `identity.json`. The keystore, permissions `0600`.
- `state.json`. Servers, keychains, DM sessions, bounded message history
  (up to 2,000 messages per conversation and 512 conversations per category),
  and the encrypted-at-rest pending message outbox.
- `node_identity.json`. A headless node has no user message secrets, but this
  file still contains its libp2p routing identity. It is stored plaintext with
  permissions `0600` and must be protected as an operational credential.

## State transfer and hardening

The sealed local state can be exported as an encrypted package and imported
into another installation while locked. Import validates the package envelope
and atomically replaces the local file; the recovery phrase still has to unlock
it. Automatic background synchronization is not implemented yet.

Sealed DM envelopes carry a random per-process session nonce. It is mixed into
message-key derivation, so two devices restored from the same recovery phrase
do not reuse the same key/nonce pair. Legacy v1 envelopes remain readable;
replay state resets when a new session nonce arrives.

Relay topic requests have a global cap, a per-peer cap, and an expiry. Observed
external addresses must be public IP addresses before they can be advertised.
Incoming history is persisted before delivery ACKs are published, and blob
responses are hash-checked before storage.

## Group DMs and attachments

Group DMs use signed group descriptors containing the owner key, member peer
IDs, X25519 keys, and a membership revision. Invitations are delivered inside
sealed direct-message envelopes; the group topic is derived from the group ID,
not hosted by a directory or relay.

Group attachments up to 8 MiB are supported. Small files use one sealed
multi-recipient group envelope; larger files are split into independently sealed
24 KiB chunks. Group payloads carry the membership revision, each chunk is
acknowledged separately, duplicate chunks are ignored, and incomplete transfers
resume from sealed local state.

Direct-message attachments up to 8 MiB are supported. Small files use one
sealed DM envelope; larger files are split into independently sealed 24 KiB
chunks. Each chunk is acknowledged separately, duplicate chunks are ignored,
and incomplete transfers are kept in the sealed local state so they can resume
after restart. Channel attachments are raw DHT blobs and are not E2E encrypted;
files up to 8 MiB use signed 24 KiB chunk manifests. Relay operators can observe
DHT hash/metadata and bytes for those channel attachments.

## Delivery state and receipts

Text DMs, group messages, and DM attachments are written to a local outbox
after local encryption succeeds. The outbox is restored on unlock,
retried by the connectivity poller, and can be retried explicitly from the
conversation header. A live publish failure does not discard the queued
message. The recipient removes an entry after sending an encrypted delivery
acknowledgement.

DM and group read receipts are separate encrypted control messages. They are
sent when the corresponding conversation is opened, update the sender's stored
read state, and do not mean that a relay or the recipient's device can read the
message plaintext. Group delivery acknowledgements remain separate from group
read receipts.
